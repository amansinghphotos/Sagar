# 11. His Two Macs Judge Each Change

Decided by the owner, by approving this pull request.

**Context.** On 27 November checks waited up to 48 minutes for one of GitHub's five Macs, and every change
was tested about four times: at each commit here, on GitHub for the request, and on GitHub again after the
merge. At least 23 of the 68 failures on GitHub's Mac were not the change's. The hidden Mac (decision 10)
tours an app in about 2 minutes against GitHub's 10 to 12, from a clean guest each time. The owner asked
for the fewest machines, programs, keys and hand-offs, and for every aspect of an app to be provable. On an
independent review's page he kept seven of its picks, and for the eighth chose that the hidden Mac take
over at once: "i wanna use the virtaul mac on my machine now and ditch github mac altogether".

**Decision.**
1. Each finished change is judged once, whole, on his Mac: every rule and test it can reach, from a clean
   copy of its commit merged with main as it stands, with the app's tour in the hidden Mac. The hidden Mac
   and his Mac have the final say; GitHub's Mac no longer checks each change, nor main after a merge.
2. GitHub keeps the code, his approvals and the releases. Its Linux checks the text rules and the request's
   words, and that the proof from his Mac names the request's newest commit. GitHub's Macs check nothing:
   before he is asked to approve a release, the hidden Mac installs the previous version and watches it take
   the update, and GitHub publishes the approved file from Linux. Until that is built, GitHub's Mac proves
   the update, once a release, and at no other time.
3. The hidden Mac takes over at once. Until the cause of macOS stopping it is found and mended, a run that
   macOS stops is started again from clean and the stop is counted and said; it is never read as the
   change's fault, and a tour that fails is never tried again without a decision of his.
4. The next three real changes are judged by both his Mac and GitHub's Mac, side by side. If the two agree
   each time, GitHub's Mac stops checking each change and main after a merge; then the loop that waits on
   its answer and the places the checks behave differently there are deleted outright, with their tests.
5. A tour may turn an app's permission switch in the hidden Mac, as a person would, so a machine proves
   every aspect of an app but his own hardware.
6. A test that fails though nothing is wrong is a fault, mended before new features.
7. A check that hangs stops itself and names the test that hung: a minute for each test, 20 for the whole.
   Launch and rest are measured in the hidden Mac. If Chete's fastest launch there is over the number
   allowed, the number is not raised in the same change: it comes to him as a choice.
8. The checking rules change only to mend a fault, and one chat changes them at a time.

**Consequences.** A change waits about 6 minutes from finished to merged, and a release no longer waits for
a run on GitHub. Nothing merges while his Mac is closed or the drive is away; a request already shown to
him still merges on his approval. GitHub no longer runs the tests itself: it trusts a reply from the agents'
app that names the commit, as it trusts the reviewer's today. Only the check command writes that reply,
every whole check runs merged with main, and a release runs the whole check on main again, so a change that
slipped through fails the next one by name. Nothing in GitHub's settings changes: the rule on main still
requires `check` and `words` from GitHub's Actions, and `check` becomes seconds of text rules on Linux. No
runner, no new program, no new key, no new right for the agents' app. Chete 1.0 ships on the old path. This replaces "GitHub's runner still judges" in decisions 6 and 10.
